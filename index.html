Act 01 • Starting With What Everyone Knows

Vibe Coding: Instant Magic Followed by Entropy Collapse

Chat prompting feels effortless for the first hour, until growing context turns improvisation into debt.

BEAT 1.1 • HONEYMOON PHASE Next: Collapse →

Prompt → Instant Prototype (“Look, It Works!”)

In single-window scripts, zero ceremony and rapid iteration shine while the whole codebase fits one prompt.

BEAT 1.2 • CONTEXT DRIFT & ENTROPY COLLAPSE Next: OpenSpec →

Why Pure Vibe Coding Collapses at Scale

  • Context Drift: Fixing Bug A breaks Feature B with no spec anchoring the model.
  • Bloat & Redundancy: Every prompt spawns parallel helpers and extra dependencies.
  • Unsafe Main Edits: Unverified experiments overwrite working files in main.
“Vibe coding is a slur — I do agentic engineering.” — Peter Steinberger (TEDAI Vienna 2026, Session 4)

Act 02 • Pillar A: Spec-Driven Contract

OpenSpec & Spec-Driven Development (opsx-*)

Separate thinking and specification from coding: every change locks into a 5-stage contract before production edits start.

BEAT 2.1 • 5-STAGE LIFECYCLE Next: Bottlenecks →

Crystallizing Chaos Into openspec/ Contracts

  • opsx-explore: Read-only thinking partner mapping code and trade-offs with zero writes.
  • opsx-propose: Generates proposal.md, delta specs/, design.md, and tasks.md.
  • opsx-apply → opsx-verify → opsx-archive / opsx-bulk-archive: Executes, audits scenarios, and syncs OpenWiki Mode B.
BEAT 2.2 • WHERE OPENSPEC ALONE STALLS Next: Beads + Superpowers →

Two Shortcomings in Standard OpenSpec

  • Static tasks.md (- [ ]): Plaintext checklists lack a blocked-by DAG, atomic claiming, and cross-session queries.
  • Main-Branch Overload: Standard opsx-apply edits main directly inside one bloated context window.

Act 03 • Pillars B & C: Issue Graph + Worktree Sandbox

Beads (bd) + Superpowers: DAG & Worktree TDD

Split the Control Plane from the Execution Sandbox: Beads schedules a live DAG and Superpowers builds in isolated Git Worktrees.

BEAT 3.1 • BEADS (bd) DAG Next: TDD Reactor →

From - [ ] Lists to a 3-Level DAG (.beads/)

  • 3-Level Hierarchy: Parent Epic → topic feature → atomic task (bd dep add), indexed in tasks.md.
  • Atomic Querying: opsx-apply claims ready leaves via bd ready --parent <epic-id> --exclude-type=epic,feature.
BEAT 3.2 • WORKTREE TDD REACTOR Next: OpenWiki Brain →

Isolated .worktrees/ Sandbox & TDD Queue

  • Topic Isolation (superpowers-using-git-worktrees): One .worktrees/<topic> per topic keeps main specs and .beads/ clean.
  • Sequential TDD & Single Merge: Per subtask: micro-plan → Red → Green → Refactor → git-commit, then merge once via superpowers-finishing-a-development-branch.

Act 04 • Pillar F: Institutional Memory SSOT

OpenWiki (openwiki/): The Project’s Neural Brain

Across dozens of features, agents suffer architectural amnesia. OpenWiki is the human- and AI-readable SSOT for durable project knowledge.

BEAT 4.1 • MULTI-ARCHETYPE ENCYCLOPEDIA Next: 3D Brain →

Structured Knowledge Domains (openwiki/INSTRUCTIONS.md)

  • Archetype A (System & Code): Architecture, ADRs (adr/), Caveats (caveats/), and Runbooks (runbooks/).
  • Archetype B (Research) & C (Theses): Primary sources, Attribution Hygiene, value loops, OKF v0.2 frontmatter, and .claims/ sidecars.
BEAT 4.2 • SYSTEM 1 RADAR → SYSTEM 2 READ Next: Ponytail + Git →

OKF v0.2 vs. Chunked RAG: Radar → Lossless Read

  • System 1 Radar (<50 ms, Mode A (Read Protocol)): Unlike chunked RAG (which drops bottom-of-file caveats), wiki_scout.py runs zero-dep SQLite FTS5 BM25 over quickstart.md & index.md to return a ~1 KB map with lines=[...].
  • System 2 Lossless Read & Mode B: Agents read full ADRs & caveats (in each Bead Execution Packet) — zero vector DB — while opsx-archive syncs insights via Mode B (/openwiki:update).

Act 05 • Pillars D & E: Quality & Safe Persistence

Ponytail + git-commit: Anti-Bloat & Diff Airlock

Two cross-cutting gates keep implementations minimal and every commit free of leaks.

BEAT 5.1 • PILLAR D: PONYTAIL LADDER Next: Laser Airlock →

“Rigorous About Reading, Lazy About Writing New Code”

  • Walks 7 rungs and stops at first fit (click R1–R7): 1. YAGNI → 2. Existing Codebase → 3. Stdlib → 4. Native Platform → 5. Installed Deps → 6. One-Liner → 7. Minimal Code.
  • Protected Non-Negotiables: Validation, security, accessibility, and automated tests stay intact.
BEAT 5.2 • PILLAR E: git-commit AIRLOCK Next: Symphony →

Audits Diffs & Writes Clustered [AI] Commits

  • Scans git diff --unified=0 to block PII, secrets, and absolute paths, then clusters by module:
[AI] feat(bd-a4f.2): add token cache and expiry tests
* src/auth:
- src/auth/token_cache.py
- implement TTL token cache using stdlib time.monotonic
* tests:
- tests/test_token_cache.py
- verify cache hit, expiry eviction, and secret redaction

Act 06 • Closed-Loop Synthesis & Quantified Impact

The Complete Symphony: Compounding Engineering

Together, the Six Pillars turn AI coding into a self-reinforcing loop where every change makes the next one safer and faster.

BEAT 6.1 • CLOSED-LOOP SYNERGY Next: Quality KPIs →

Control Plane ↔ Execution Sandbox Synergy

  • Control Plane (main): OpenWiki grounds context → OpenSpec locks the contract → Beads schedules the DAG.
  • Execution Sandbox (.worktrees/): Superpowers runs TDD → Ponytail trims bloat → git-commit seals diffs → OpenWiki absorbs ADRs & caveats.

Neopallium: Maintainability, Hygiene & Continuity KPIs
